# RFC 030 Step 0 — Verify the Split Before Any Code

RFC: `rfcs/accepted/030-two-crates-behind-one.md` (accepted by the owner, 2026-11-04). Analysis: `.git-exclude/reviewed/086-architect-crate-split-question-2026-11-04.md` (read it first: it records what was measured and what was not).
Start once the v0.24.0 release candidate is pushed (you will be waiting for the owner's authorization). This is **verification and measurement only**: no tracked file changes, everything under `.git-exclude/tmp/`, prototypes in a scratch worktree of a **committed** tree (the v0.24.0 candidate or, when it exists, the v0.24.0 tag), which you delete afterwards. Do not touch `Makefile.toml`, the workflows or `Cargo.toml` of the real tree.
Format of the review request: `rfcs/handoffs/025-error-taxonomy-and-input-validation/implementation-handoff.md` § 6.
Authorship: high-capability model. Authorized: the owner.

## 0. Why, and the rules

The owner accepted a split into `localcache-format`, `localcache-storage` and the unchanged facade `localcache`, on three conditions the RFC writes as stop rules: (a) an internal crate whose API cannot be written plainly stays a module; (b) the error mapping must be one to one; (c) if Miri/fuzzing and CI time give nothing, the case rests on enforced layering and least privilege alone and the owner decides with that stated.
You report; you do not decide whether the split goes ahead. Be adversarial: look for the reason a boundary does not hold (a function that needs a foreign type, a feature that cannot be forwarded cleanly, a test that reaches across). Use the same toolchain as CI, a stated host, and log `/proc/loadavg` at the start of every timed round.

## 1. What to establish, each with a command, its output and an exit code

1. **The public API sketch of each internal crate** (RFC R3). For `localcache-storage`: a `Store` (the connection plus the statements) and the types it returns, mapped from today's `db::repository` free functions, `db::schema` (initialize, classify, migrate, configure), `db::indexes`. For `localcache-format`: `seal`/`open` over a `Key`, `encode`/`decode` over a codec and a tag, the tag table, compression and JSON. Write the sketch as real Rust signatures in a scratch crate that compiles (bodies `todo!()` are fine), run `cargo doc` on it, and report:
   the count of public items; whether any public function names a type of another internal crate (it must not); whether any `#[doc(hidden)]` item is needed (it must not); whether it fits one rustdoc page. Give the mapping table: each current `pub(crate)` function → the new item, or "stays in the facade", with the reason.
2. **The per-layer errors.** Assign every variant of `LocalFileCacheError` to `FormatError`, `StorageError` or the facade; show where one variant is produced by two layers (and what the mapping does). Generate the golden table (variant, `Display` text, feature gate) from the v0.24.0 tree with a test, and show the table the new mapping must reproduce. Include `DatabaseError` (opaque, wraps `rusqlite`'s error) and the `SqliteResultExt` helper.
3. **Miri and a fuzzer.** First, in the **present** crate, do the codec's and the sealing's unit tests run under Miri when filtered to tests that never call SQLite (`cargo +nightly miri test -p localcache --all-features -- <filter>`)? Report the exact command, the output and the time (install Miri in a scratch toolchain if absent and say so). Then in a scratch crate holding a copy of `payload_codec`, the tag table and sealing: do the unit tests run clean under Miri, and how long; a `cargo-fuzz` (or `libFuzzer` via `cargo fuzz`) target for `from_slice` and for `open`, run for ten minutes each: crashes found, if any, with the input. If a tool is not installable offline, say so and stop that item.
4. **CI time.** On the scratch worktree, split the code as the RFC says (a prototype is enough: it need not pass every test, but it must build and run the format and storage tests and the facade's tests that still apply). Time each row of the present `gate-features` (each-feature rows, the two suite rows, the CLI) and the same rows after the split, cold and warm, with the host's core count stated; also with the core count limited to 2 and to 4 (`taskset` or `-j`) to approximate the CI runners. Report the totals against the CI's 530 s for the feature matrix and say which rows moved to which crate.
5. **The publish rehearsal.** In the scratch worktree: `cargo package` and `cargo publish --workspace --locked --dry-run` for four crates (the two new ones, the facade, the CLI); the order cargo chose; what the `Release` workflow's digest steps and the `github-release` guard need to count four `.crate` files (list the lines, do not edit them); what `scripts/check_versions.py`, the archive and the advisories gate need to learn the new crates.
   **Trusted Publishing for a crate name not yet published:** from the crates.io documentation (cite the page and the date you read it), how a trusted-publisher record is created for a name that does not exist yet (a pending record, or a first manual publish); what the owner must do, step by step, and whether the `Release` workflow as it is would publish the first version. If the answer is "a first manual publish with a token", say so plainly: the RFC is amended before the release, not improvised at it.
6. **The hit path.** `get` (hit) and `set` through the engine on the prototype against the v0.24.0 tree, a 64-byte and a 1 MiB payload, with and without encryption, alternating arms, at least seven rounds, `/proc/loadavg` logged. Report the paired difference with its spread. Cross-crate calls are not inlined without `#[inline]` or LTO: say whether the prototype needed any `#[inline]` and where.
7. **Rendering.** That `#[doc(inline)]` re-exports of the types that moved (`EntryInfo`, `Codec`, `DatabaseError`) render in the facade's rustdoc exactly where they do today (compare the HTML page list and the item declarations of all pages with the v0.24.0 tree), and that the intra-doc links in the book and the rustdoc still resolve (`RUSTDOCFLAGS="-D warnings" cargo doc --workspace --all-features --no-deps` and the no-default-features build).
8. **The relocation list.** Which of the 24 integration tests, the unit tests, the fixtures and their generators, the golden vectors and the benches move to which crate, which stay, and which cannot move without the sketch of item 1 growing. A test that reaches into `pub(crate)` internals of another layer is a finding.
9. **Feature forwarding.** `compression`, `json` and `encryption` forwarded from the facade to `localcache-format` (and `json` to `serde_json` for the query layer): show that every feature row builds, that `cargo tree -e normal` with no features shows neither `zstd` nor `aes-gcm` nor `zeroize`, and the `--no-default-features` build of each crate alone.

## 2. The report

One review request: `.git-exclude/review-request/NNN-dev-rfc030-step0-<date>.md`, with each of 1 to 9 answered with evidence, then:
- **Findings that contradict the RFC**, each stated plainly (the architect corrects the RFC);
- **An estimate** of the production lines moved, the new lines (the facade's glue, the two error types, the `Store`), the files touched, and the order of the work in slices that each build and pass all tests;
- **The three stop rules**, each answered yes or no with the evidence that decides it;
- a one-paragraph verdict. You report; you do not decide.

## 3. Not yours

Any change to a tracked file; the implementation; the version; the decision to proceed, to drop a crate, or to take stage 2 (the adapters).

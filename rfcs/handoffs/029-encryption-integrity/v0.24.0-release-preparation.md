## 1. The changes, in this order

1. **A commit `docs: how to recover when a rotation fails (RFC 029)`.** Review found a gap in the book. `rotate_encryption_key` is all-or-nothing, so one entry that cannot be opened (damaged, moved from another path, or sealed under another key) makes the whole rotation fail with `EncryptionError`, and the error does not name the entry (a stored path is never echoed into an error).
   I ran it: on a keyed engine, `query().run_report()` lists such entries in `skipped` with their path and error (an unsealed entry is also listed, but that is harmless: the rotation seals it). Say so, once in `migration.md` (after "Who must act, and how"), and by link in `errors.md` (`EncryptionError`) and the `rotate_encryption_key` rustdoc:
   if a rotation fails with `EncryptionError`, run `query().run_report()`, remove the entries it lists with an `EncryptionError` (`remove`), and rotate again; `UnsealedEntry` entries need nothing. One line in `migration.md` and `features.md` that after the rotation an engine without a key gets `MissingEncryptionKey` for **every** entry of the namespace, a formerly plain one included (your request 063 § 4.8). A test that does exactly this (swap one entry, rotation fails and changes nothing, `run_report` names the entry, `remove`, rotation succeeds) belongs in `tests/encryption_integrity.rs`.
2. **A commit `docs: fix the intra-doc links that break without default features`.** Your request 064 § 3.3: three unresolved links (`engine.rs` `set`'s `EncryptionError`, `query.rs` `run`'s, `pool.rs:60` `AsyncCacheEngine`). Fix them (plain code spans for a feature-gated item) and add `RUSTDOCFLAGS="-D warnings" cargo doc -p localcache --no-default-features --no-deps --locked` to the `gate-docs` task in `Makefile.toml`, since the gates built docs only with `--all-features` and nothing caught it. Run it with each single feature too if it is cheap (`--no-default-features --features <f>` for the ten features) and report which, if any, fail; fix only what you find in this task's three.
3. **The version, as its own commit `chore: prepare v0.24.0 (version, install examples, changelog)`.** `Cargo.toml` → `0.24.0`; `Cargo.lock` follows (report its diff in full); every install line in `README.md` and `docs/src/` → `0.24.0` (`python3 scripts/check_versions.py` is the gate). In `CHANGELOG.md`: `## [Unreleased]` becomes `## [0.24.0] — Unreleased` with `*Date set at owner authorization.*`; the link references at the foot (`[Unreleased]` compares `0.24.0...HEAD`, `[0.24.0]` compares `0.23.1...0.24.0`).
4. **An upgrade list at the head of the `[0.24.0]` section**, "Upgrading from 0.23.x, in this order", pointing at the entries below and adding no claim: (1) if you have an encryption key and a database: call `rotate_encryption_key` once per namespace with the same key; (2) do not rotate with an older version afterwards; (3) one key per trust domain; (4) code that matches on `LocalFileCacheError` (new variant `UnsealedEntry`; the enum is `#[non_exhaustive]`); (5) a keyed import accepts only bound records; (6) queries on a keyed engine never use the SQL pushdown.
